# USPSA Population Analytics Engine v2

A four-layer pipeline that turns PractiScore match results into two analyses:

1. **Division trends over time** — Carry Optics, Limited, Limited Optics, and Open participation (counts and share of the whole field) across a time frame you select.
2. **Classification vs classifier difficulty** — for every classifier stage (`99-11`, `03-05`, ...) found in your data, how GM/M/A/B/C/D/U shooters performed, plus a skill-adjusted difficulty score per classifier.

```
scrape.py ──► data/raw_reports/*.txt ──► report_parser.py ──► SQL (db.py) ──► analytics.py ──► dashboard.py
 Playwright     PractiScore Web Reports     $INFO/E/G/I lines     SQLite/Postgres     pandas + Z-scores    Streamlit + Plotly
```

## Quickstart (no scraping needed)

```bash
pip install -r requirements.txt
python check_setup.py          # preflight: folder, deps, browser, DB
python seed_demo.py            # synthetic 18-month season → data/uspsa.db
streamlit run dashboard.py     # opens at http://localhost:8531
```

The demo data is generated by `seed_demo.py` and is **synthetic** — the trends it shows are invented and exist so you can exercise every chart before harvesting anything real.

The UI ships with a dark "shot-timer" theme (`.streamlit/config.toml`, loaded automatically when you run from the project folder): brass-amber monospace readouts, a GM→U classification ribbon under the title, end-of-line division tags instead of legends, and an insight strip that answers the headline questions in plain language — fastest-rising division, steepest slide, and hardest classifier — computed live from whatever date range is selected.

## Real-data workflow

```bash
playwright install chromium    # one-time browser download
python scrape.py               # opens a visible browser
```

Step 1 — a real Chromium window opens on `practiscore.com/search/matches`. You clear the Cloudflare check if it appears, set **match type = USPSA**, pick **your date range**, hit Search, and page through the results. This is where the "user-selected time frame" lives: you select it in the site's own UI, and the script harvests every `/results/` link that renders while you browse. Press **Enter** in the terminal when done.

Step 2 — the script visits each harvested match page, follows its **Web Report** link (`practiscore.com/reports/web/...`), and downloads the plain-text report using the browser's own authenticated session, with a jittered ~3 s delay between matches. Raw files land in `data/raw_reports/` and are cached, so re-runs only fetch what's new.

Step 3 — every report is parsed and loaded into SQL, then `streamlit run dashboard.py`. The dashboard's own date-range filter lets you narrow further within whatever you ingested.

Useful flags: `--urls-file list.txt` (skip the search session; one results URL per line), `--limit 25`, `--delay 5`, `--refresh`, and `--reparse-only` (rebuild the DB from cached files with no browser at all).

## Why it's built this way

Your V6 intercepted a response whose URL contains `match-results` and read keys like `sh_name` / `sh_dv` / `sh_cls`. I could not find that endpoint or those keys in any working open-source PractiScore tooling — which is consistent with the interception never firing. What working projects actually use:

- **The Web Report text file.** The `kmcken/CompetitionShootingAnalytics` project (Apache-2.0) downloads each results page, follows the `https://practiscore.com/reports/web/...` link, and parses the returned text: `$INFO` lines for match metadata, `E` lines per competitor (classification at field 8, division at field 9, DQ at field 4), `G` lines per stage (classifier flag at field 4, classifier code at field 5), and `I` lines per stage score with the **hit factor precomputed at field 28**. `report_parser.py` follows those positions — now empirically re-verified, with one correction, against 49 real reports (see *How this was verified*) — and adds a per-line sanity check (HF can never exceed points ÷ time, since penalties only subtract), so a silent column shift gets flagged loudly instead of corrupting your metrics.
- **No official API, and hardening over time.** PractiScore staff state there is no API and no sanctioned scraping; a 2024 community thread documents direct `results.json` pulls that used to work now returning Access Denied ([community.practiscore.com, "Programmatically Pulling Scores"](https://community.practiscore.com/t/programmatically-pulling-scores/14836)). Older tools (`unibrain1/Parse_Practiscore`, `jeffersonjhunt/ppull`) pulled from the public S3 bucket `s3.amazonaws.com/ps-scores/production/{uuid}/…`; treat that path as historical, not guaranteed. The site also sits behind Cloudflare (your own experience; other projects either handle a Turnstile widget or pay for unblocker proxies), and its `robots.txt` disallows automated crawling.

So the design leans into the one thing that is clearly fine: **a human using a real browser.** You drive the session; the script observes it and then makes a small number of polite, authenticated requests for the same report files a person would click. Keep volumes modest, keep the delays, and don't redistribute the raw data.

**Endpoint discovery, instrumented.** Your open blocker was identifying the real search/results endpoints. While you browse, every JSON response the site produces is appended to `data/discovery_log.jsonl` with its URL, status, and top-level keys. One browsing session replaces guessing an endpoint name with reading a list of the ones that actually exist — if a cleaner JSON route exists for the search page, it will be in that file.

## Database schema

Star-style layout, same shape as your PostgreSQL design: `matches` and `stages` act as dimensions; `competitors` (one row per registration, carrying division/classification/DQ) and `stage_scores` (one row per shooter per stage, carrying the hit factor) are the fact tables. SQLite is the zero-setup default; point `DATABASE_URL` at Postgres to use your existing backend:

```bash
pip install psycopg2-binary
export DATABASE_URL=postgresql+psycopg2://user:pw@localhost:5432/uspsa
python scrape.py --reparse-only     # reload cached reports into Postgres
```

Ingestion is idempotent — each match is keyed by `source_key` derived from its URL, and re-ingesting replaces that match's rows rather than duplicating them.

## Difficulty methodology (the Z-score layer)

Raw mean hit factor on a stage confounds *who showed up* with *how hard the stage is*. For each classification k, take its mean HF on every classifier c and z-score **within the class, across classifiers**: z(c,k) = (mean_HF(c,k) − μ_k) / σ_k. That removes class k's overall pace. The difficulty score is D(c) = −mean over k of z(c,k): positive means every class — GM and D alike — shot that stage below their own norm. Guards: a cell needs ≥ 5 valid runs (slider), a classifier needs cells from ≥ 3 classes (slider), a class column must span ≥ 2 classifiers (σ undefined otherwise), and DQ/DNF/zero-HF runs are excluded throughout.

`data/reference/classifier_titles.csv` maps codes to official names (e.g. `99-11`) so charts read as stages, not serial numbers.

## How this was verified

The parser was validated against a corpus of **49 real PractiScore web reports (10,497 competitors, 126,629 score rows, 2022 Level I–II USPSA matches)**: all 49 parse with zero skipped lines; hit factor equals total points ÷ time to four decimals in 100.0% of timed rows (fields 25/27/28 confirmed); the DQ flag is field 4 of E-lines (the only flag ever set for zero-point shooters) and field 3 of I-lines (all 3,057 set rows had zero HF and belonged to match-DQ'd shooters). The audit also caught a real bug inherited from the reference parser: **I-line field 4 is not DNF** — it's a near-constant per-match app flag that is "Yes" on ~60% of valid scores, and trusting it would have silently discarded most classifier runs. DNF is now derived (no time, no points, no HF) instead of read.

The scraper was executed end-to-end — real Playwright, real Chromium — against a local mock of practiscore.com serving those real report files: search-page harvest, authenticated web-report download via the browser context, the `/results/html/ → /results/new/` fallback, parsing, and DB load all ran live. Current-site evidence (a June 2026 open-source Chrome extension built against PractiScore) confirms `results/new/{id}` is still the results URL pattern and Cloudflare interstitials are still present.

**The one thing that could not be verified from here:** the exact present-day DOM of the live search page behind Cloudflare. The harvest deliberately depends on almost nothing (any anchor containing `/results/`), and every JSON response is logged to `data/discovery_log.jsonl`, so if the page differs, one browsing session shows you exactly what it returns instead. Failures are loud and per-match, never silent.

Three of the real reports ship in `data/raw_reports/`, so `python scrape.py --reparse-only` loads genuine match data with no browser at all.


## Troubleshooting a live run

**Nothing downloads / everything skips.** Read the per-match reason; each names its own cause.

| Message | What it means | Fix |
|---|---|---|
| `skipping IPSC match` | Correct behavior — the search wasn't filtered to USPSA | Set match type to USPSA in the search UI, or pass `--allow-non-uspsa` |
| `Cloudflare challenge` | Session went stale mid-run | Click through the check in the open browser window; re-run (cached files are skipped) |
| `login required` | PractiScore wants an account for that report | Sign in inside the browser window, then re-run |
| `no Web Report link found on any results view` | Tried `/results/all/`, `/new/`, `/html/` — none had one | Usually a non-USPSA or scores-not-posted match |

Blocked responses are saved to `data/debug/*.html` so the cause is inspectable rather than guessed at.

**Wrong app opens / familiar filenames from another project.** This project uses ordinary names (`dashboard.py`, `config.py`, `analytics.py`) that other Python projects also use. If it shares a directory with another codebase, `streamlit run dashboard.py` can launch the *other* project's dashboard, and imports can cross-wire between the two. **One project per folder is the rule.** The safeguards: every entry script refuses to run if the `config.py` it finds isn't this project's (clear STOP message instead of a traceback), `python check_setup.py` names any file in the folder that belongs to a different project, and the dashboard is pinned to its own port (8531) so it can't be confused with another Streamlit app on the default 8501.

**Schema note:** the `matches` table gained a `region` column. If you have a database from an earlier build, delete `data/uspsa.db` and re-run `python scrape.py --reparse-only`.

## Study guide

Since the point of this project is that you can rebuild it: `scrape.py` is the asyncio + event-listener material (compare `harvest_search_session`'s background task to your V6 `page.on("response")` handler); `report_parser.py` is defensive parsing of an undocumented format; `db.py` is SQLAlchemy 2.0 ORM with cascading idempotent upserts; `analytics.py` is where the Z-score normalization from your original design actually lives — read `difficulty_scores` until you could derive it on paper; `dashboard.py` is presentation only, no math.
